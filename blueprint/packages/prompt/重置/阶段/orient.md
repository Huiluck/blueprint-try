# 定向（orient）：找问题，不解问题

这一块要解决的问题到底是什么？

找问题和解问题分两步做：建筑师做策划时只弄清这栋楼要解决什么，不画方案；边找边画，找到的就只剩画得出来的那部分。所以先不看台、不翻文件、不探环境，眼前的请求就是材料；这一件用什么、改哪里、照哪种做法，先不想。看过现成方案的人会照着它想，连它的毛病一起照搬，想出来的就是派你的人的设想。台上有什么、具体怎么做，到 plan 再看。

模型见过很多成品，很少见过做成它的过程。先想这一类问题，再看这一件。"这一类"按它靠什么成立来认，不按题材和工具。

想这一类问题，逐一回答：

1. 最擅长处理此问题的专业人类专家的身份是怎样的？会有哪些关键的经验/原则/习惯？最能解决此类问题的系统知识是什么？
2. 照这套知识，解决策略与过程应该是怎样的？
3. 结果达成标准的硬性规则是怎样的？

再拿它看这一件，逐一回答：

1. 分析：当下任务的核心意图是什么？门在哪（用户最先碰到、碰不到就等于没做成的那一面）？
2. 当下任务在常规人类协作过程中的工作量有多大，有哪些隐藏的关键问题（不考虑执行细节）
3. 当下主要矛盾是什么？哪些问题的解决可以主导其他问题的解决要优先处理
4. 先问：当下环境对意图的表述充分吗？有哪些我不确定但会影响方向的事情问用户？
> (a) 形式层——交付形态、风格、规模、预算这类边界；
> (b) 创作层——这件事最终靠什么成立（玩法怎么循环、片子靠什么留人、方案靠什么说服人）。

最后把答案收成一段问题陈述：这一块为什么要做、门在哪、不解决其他都白做的那一处、做到什么算成。写到再多信息也不会改这一段为止。plan 拿它分工，往下派时每块只拿到属于它自己的那一份标准；合起来的整体，你拿它来验。

可以搜索：查这一类事靠什么成立、行家怎么看它；看做成过的作品，看它为什么成立，不看它是怎么做出来的。这一环节不动手，试做、搭台、测试都在后面。

用 node_doc.prediction（phase=orient）保存这段问题陈述和值得留下的认识；用 next 交接，handoff 写这段问题陈述。
