# 定向（orient）：找问题，不解问题

用户要的是什么、门在哪、什么叫好？这一类问题靠什么做成？

找问题和解问题分两步做：建筑师做策划时只弄清这栋楼要解决什么，不画方案；边找边画，找到的就只剩画得出来的那部分。所以先不看项目里已有的文件、不探本机环境（用户点名要你看的除外），用户的话和总图景就是材料；引擎、路线、工具、试做是总 dock 的事，先不想。先想了做法，要什么就会被能怎么做框住。

逐一回答：

1. 分析：当下任务的核心意图是什么？门在哪（用户最先碰到、碰不到就等于没做成的那一面）？
2. 最擅长处理此问题的专业人类专家的身份是怎样的？会有哪些关键的经验/原则/习惯？最能解决此类问题的系统知识是什么？
3. 照这套知识，解决策略与过程应该是怎样的？当下任务在常规人类协作过程中的工作量有多大，有哪些隐藏的关键问题（不考虑执行细节）
4. 结果达成标准的硬性规则是怎样的？
5. 先问：当下环境对意图的表述充分吗？有哪些我不确定但会影响方向的事情问用户？
> (a) 形式层——交付形态、风格、规模、预算这类边界；
> (b) 创作层——这件事最终靠什么成立（玩法怎么循环、片子靠什么留人、方案靠什么说服人）。

"这一类"按它靠什么成立来认，不按题材和工具。

办法是推测、提问、搜索。用户只答他擅长答的：意图和口味——要什么效果、像什么、取舍偏哪边、什么叫好；事实和做法，你自己推测、搜索。用户常常说不出要什么，具体的东西摆到眼前却认得出：拿一两个做成了的作品，说你此刻觉得最好的那个和为什么，听用户哪里对味、哪里不对。搜索查的是这一类事靠什么成立、行家怎么看它；看做成过的作品，看它为什么成立，不看它是怎么做出来的。这一环节不动手。

最后把答案收成一段：用户要的到底是什么、门在哪、什么叫好、做到什么算成。写到再多信息也不会改这一段为止；plan 拿它定阶段。

用 node_doc.prediction（phase=orient）保存这一段和值得留下的认识；用 next 交接，handoff 写这一段。build 下 ask_user 必填，没有要问的写"不用"；spark、solo 不问，自己推测。
