# 校准定稿（plan）

达成的过程清不清楚，要不要分阶段？本阶段回答什么、做到哪就够、靠什么策略做成？

逐一回答以下问题

1. 思考：当下主要矛盾是什么？哪些问题的解决可以主导其他问题的解决要优先处理，是否应该分轮
2. 要做成用户要的东西，得依次回答哪几个问题？本阶段回答哪一个，做到哪就够？
3. 本阶段靠什么策略做成？
4. 怎么推进效率最高？哪一步最先碰到现实，前面做的后面能留下多少，哪些能照搬做成过的？答到换一种推进法也省不下什么为止。

分轮一般对应几种情况
1. 有可以主导后续选择的重要关键信息需要优先执行。
2. 决定先测试狗窝，但是狗窝的水准无法达成最终验收标准。

## 把不清楚变清楚

过程不清楚，是中间藏着没想到的步骤。有五种办法把它挖出来：
- 试：先做便宜的版本碰现实，比如先测狗窝。
- 反推：从目标倒着问，前一步必须成立什么。
- 照搬：找做成过的类似的事，借它的过程。
- 简化：先解简单版，再加回细节。
- 问：意图和口味问用户；事实和做法自己推测、搜索。

先对付那个答出来最能改变后面决定的未知，也就是主要矛盾。

## 阶段

每个阶段回答一个问题，答完以后"够"变了，哪几块值得做、做到哪也跟着变。比如一部三分钟的动画短片：先用分镜、方块角色和临时音乐拼一版，看故事立不立得住，这时角色不建模，音乐不作曲；再定角色和美术风格，做透一场关键戏；最后铺满全部镜头、配乐和混音。不分，几个人一开始就全量开工，等角色绑好、音乐作完才发现故事撑不住，前面做的大半要重来。上面分轮的第 2 种情况，就是先分出这样一个阶段。

眼前这一段要清楚，后面的先写个大概。目标一开始就清楚、一两步就完，或者方向已定、只差照着做的，一个阶段就够；越复杂、方向越没试出来，越值得分。

## 交出去

用 divide 派出这一阶段：stage 记阶段，不记就是一个阶段；whole 写用户要的东西和这一阶段要回答的问题；blocks 只写一块，交给这一阶段的总 dock，role 写 dock，照 canon「派下级」写做什么、之间的联系、项目情境、工作等级，必要规则有才写；怎么做、怎么验由它定。它的空间是整份成品，不另搭台。阶段变了，系统开新的总 dock。

向用户输出一段简要的问题讲述结论。build 下，这份阶段方案先给用户审，通过了才派出。
