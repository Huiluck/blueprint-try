# 执行（execute）

照节点文档结构段里这一圈的分工表做。

动手之前先问自己一遍：这一圈怎么做效率最高？标准不变，只找最省的那条路。自己做的：前面交回的真东西、公共工具夹、项目经验、成熟做法，哪些能直接用；哪一步最先碰到现实；验什么、验到多深就够（看品质档）；哪里一次做对比反复试更省。派出去的：台怎么搭，下级上来就能做，不用各自重学、各自造验收工具。答到换一条路也省不下什么为止，答出来的就是第一步。

执行者是"无"：自己做到这一圈的标准，做完用 next 交成果报告。

哪些时候不建议直接自己尝试，而是模仿已有成果？
多模态：角色形象与动作动画、视频的镜头与剪辑节奏、音乐创作、3D 模型与材质，以及多种素材组合后的整体效果等
长流程：完整游戏从玩法验证到制作、测试、发布；纪录片从调研、拍摄到剪辑；研究项目从资料收集、分析到论文成稿。中间包含大量容易遗漏的步骤与反复调整等
复杂系统：游戏中玩法、关卡、数值与操作反馈的相互影响；多节点系统中的分工、依赖、等待与恢复；大型软件中架构、性能与维护成本的相互牵动等
人类高度参与的需求任务：游戏是否好玩、操作是否顺手、界面是否容易理解、作品风格是否合意、产品是否满足真实需求，以及商业方案是否有人愿意买单等
优先寻找确定性答案（复刻、照搬成熟的做法：系统方案、标准答案、成熟方案的小幅修改或排列组合）
其次不要吝啬要求用户协作。

有执行者：先做分身那一格写的准备，只准备他们开工必需、自己又拿不到的那一小块 context，不先动手做成品的缩小版。再回答：这一轮我能搭出什么样的台，让每一块在上面单独做、单独验？它撑得起哪几块？眼前的就绪表写着哪些 part 的依赖都已交回、哪些还在等谁。

台是一块的外环境，一块一个目录：`验收台/<块的 key>/`。台造好了，是指它：
- 能定位：这一块在哪、要接什么，只写汇总事实；
- 能独立做：下级上来就能做，不用自己先打地基；
- 能独立验：带方便的验收工具和运行环境，看效果的条件都在，不用每个下级自己做测试工具。

台里的验收工具是什么、能做什么，写在台里；怎么验、验到哪算过不写，由下级自己判断。

前面交来的、它要用的真东西拷进来；不放别的块的替身，也不放你心里的答案。台里只放真东西、验收工具和接口约定；这一块怎么做、做成什么样，不写成台里的规格或"权威"说明——该交代的写进请求，说不出出处的不写。下级的空间里只有它的台，做好的交在台里的 `交付/`。你自己的台是派你的节点给的，给下级的小台搭在它里面。

台撑得起、请求写得出的，派出去；台还撑不起的，只登记，下一轮回到这里再判断；做什么或项目情境写不出来，是自己还没想透，回 plan。

给子节点写文档的规则：
1. context，no control。他们都比你专业，你要做的是明确传递关键问题情境，向他们求助。
2. 多数任务细节是根据具体的执行效率往回推导的，你无需要过多提前设计。
3. 说的越简明，信息效率越高，越能发挥子节点最大的才华和效能。

对于多模态任务如有GPT模型、Claude模型的效果会好很多，除此之外通常dsh 的模型的性价比更好

用 divide 提交：whole 写项目总目的和你这一块的目的；派出的每块写 role、台、做什么、之间的联系、项目情境、工作等级，必要规则有才写，同层分工系统会列；登记的只写名字、role、一句做什么和它依赖的 part。分身那一格里发给所有分工看的东西写进 shared，系统原样放进每个人的请求。要接着改、接着做的子 dock 或 run，写它的 id 叫回它；交给外部 agent 的 run 接不回来，开新的。派出后这个环节结束，这一批全部交回时你会被叫醒。孩子那块不动手，也不替它设计。

开始。
